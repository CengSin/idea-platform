# 用 idea_platform 自身验证迭代流程

本轮已经完成：精简创建字段和接入说明、生成提醒标签、持久化分析队列、外部执行器领取/心跳/回传、用户验收与停止。以下是下一轮讨论项，尚未自动修改公开需求或执行部署。

当前平台公开记录中，根想法 `idea_jkGFFFit` 为 `idea_platform`；子想法 `idea_wslnU0tz` 为 `idea-agent`，来自作品 `work_xOn0zVYF`。子想法说明仍包含“提2~3个可能的下一步实现想法”，而本轮用户已经改为提醒标签。这说明会话中的新需求与平台需求之间存在版本差异。

1. **需求版本与变更记录。** 每轮运行应绑定需求修订号。用户临时调整范围后，需要更新需求并标明旧任务是继续、重排还是作废；不能只更新最新进展。本轮执行队列保存任务与条件快照，但尚无完整的需求修订/对比机制。
2. **子想法与代码项目绑定。** `idea-agent` 应在现有 `idea_platform` 仓库上迭代。现在执行器通过启动目录选择仓库，平台尚未记录仓库身份、基础提交、分支或工作区，也不能协调两个子想法同时改同一份代码。建议默认继承来源项目，再允许显式另起项目。
3. **验证与部署是不同状态。** 本轮本地测试、构建通过，不等于线上部署完成。运行报告已能保留文字证据，但尚无独立的 commit/PR、测试结果、预览地址与线上版本关联；作品 `published` 也不代表用户已验收。
4. **提醒需要更完整的证据。** 当前模型只看到作品说明、已同步进展、阻塞和已有子想法，不读取真实仓库、PR、测试流水线或用户反馈。先补入结构化证据再拓展建议能力，避免从简介猜需求。
5. **从验收到下一轮的决策入口。** 当前用户验收后可以创建子想法、承接并加入队列，但这些仍是分散操作。建议提供“验收并写下一步”，把提醒带入可编辑需求，保留现有发布确认，而不自动公开。

建议先解决第2项，并连同第1项实现：让一次运行明确对应哪个需求版本、哪个仓库以及哪个基础版本。这样当前项目自身的子想法迭代才能稳定复现。
